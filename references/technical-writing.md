# 技术文档指南

## 先判断读者需要哪种帮助

确定读者的角色、已有知识和当前任务。开发者可能熟悉编程，却不了解这个产品；运维人员可能熟悉日常操作，却第一次处理某种故障。解释完成当前任务所缺的知识，沿用读者熟悉的专业术语。

| 读者需要 | 文档类型 | 组织方式 |
| --- | --- | --- |
| 通过实践学会一项技能 | 教程 | 给出可完成的学习目标，沿一条明确路径操作，在关键节点说明会看到什么 |
| 完成一个已有目标 | 操作指南 | 写清适用条件、必要准备、操作顺序、分支和完成标准 |
| 查找准确的技术事实 | 参考文档 | 按接口、命令或配置项排列，以一致的字段说明行为、限制和示例 |
| 理解机制或判断取舍 | 解释文档 | 从问题和已有概念出发，说明组成、关系、原因与适用边界 |

一篇文档可以服务多种需要。短文用清楚的小节分开，长文把详细参考和背景解释放到有明确链接的页面。按当前任务调整所需部分，无须为套用分类重组整个文档库。

教程选取一条可靠、能看到结果的学习路径，提供必要的起始材料。操作指南面向已有目标的读者，把篇幅留给实际决策与操作；完整参数清单和深入原理可链接到对应说明。两者都让读者知道从哪里开始、到哪里算完成。

## 确认适用范围与事实依据

从材料中确认产品或组件、适用版本、运行环境，以及影响使用的权限和依赖。只交代会改变读者选择或操作的信息；如果文档面向特定版本，就按该版本核对行为。

起草时，从用户材料、匹配版本的官方文档、接口定义或可核查的实现中获取技术事实。改写时，保留原文的版本范围与行为；发现冲突，指出具体差异和所依据的材料。缺少参数、命令或处理办法时，把缺口列为编辑说明。仅润色语言时，可完成其余内容，无须擅自扩展为技术调查。

区分已发布行为、设计提案和实验结果。功能“计划支持”时保留计划状态；接口已接受请求时，继续按材料说明任务何时完成；性能结论附上已有的测试条件、指标和比较对象。

## 把操作写到能够完成

标题直接写任务，如“导出审计日志”。开头交代适用场景和必要准备，再按依赖顺序写步骤。

- 在动作前说明位置和条件，如“在项目根目录……”“状态为 `READY` 时……”。切换终端、主机、账号或界面时重新点明位置。
- 每一步对应一个动作或紧密相连的小操作，用“打开、设置、运行、检查”等动词写清要做什么。确认、保存和应用设置等收尾操作也属于步骤。
- 条件分支把条件和动作写在一起。可选步骤标明“可选”；不同平台或操作方式分组呈现，供读者选择一条适用路径。
- 把覆盖、删除、中断服务或产生费用等已知影响放在对应操作之前，说明受影响的对象。准备、恢复和清理方法以已有材料为准。
- 在关键步骤后给出可观察的结果，如文件生成、状态变化或界面显示。说明结果如何支持下一步，区分中间状态与最终完成状态。

错误处理紧邻可能失败的步骤，或链接到具体的排查条目。长流程按阶段组织，阶段名写明结果，让读者中断后也能找到继续的位置。

## 让命令和示例可用

先说明示例要完成什么，再展示内容。代码和命令用带语言标记的代码块，输入与输出分别呈现；界面标签、参数名和错误码保留可检索的原文。

新写的可执行示例应包含所需的上下文，如工作目录、导入、变量定义、输入文件或配置位置。多段示例沿用相同的资源名和状态。语法说明、伪代码和省略了内容的片段明确标注用途，使读者能判断是否可直接使用。

需要用户替换的值说明含义、取得位置和格式。沿用材料或项目的占位符写法，并区分用户需要替换的值与程序会展开的模板变量。例如，命令中的 `OUTPUT_PATH` 可能需要替换为文件路径；提示文本中的 `{count}` 可能由程序填写，具体以材料为准。

代码中的引号、空格、缩进、大小写和续行符按原有语法保留。编写多平台命令时分别注明适用的 shell。语言润色中发现可疑命令，保留原文并指出待核实位置；技术修正按用户要求另行核对。

示例输出标明“示例输出”，解释影响判断的字段；时间戳、标识符等可变化的值按已知行为说明。验证时区分“已对照材料核对”“已检查语法”和“已实际运行”。只有实际运行过的内容才能报告运行结果。

## 写清接口、命令与配置

参考文档沿用产品的组织结构和真实名称。同类条目采用一致的字段，第一句说明用途或效果，补足仅凭名称和类型无法知道的行为。

根据对象选取相关信息：

| 对象 | 需要说清的内容 |
| --- | --- |
| 参数或配置项 | 名称、含义、类型、必填性、默认值、单位、合法范围或枚举，以及相互依赖 |
| 接口或函数 | 调用条件、输入、返回值、错误，以及调用产生的状态变化 |
| 命令 | 运行位置、参数组合、输出、退出状态和已知副作用 |
| 配置行为 | 配置位置、覆盖顺序、何时生效，以及是否需要重新加载或重启 |

逐项保留有区别的取值语义。省略参数、传入 `null`、空字符串、空集合、`0` 和 `false` 可能触发不同的行为；布尔值分别说明两种取值的效果。默认值写清在什么情况下采用，范围写清是否包含边界，数字附上单位。

涉及分页、异步任务、超时或重试时，交代会影响正确调用的行为：如何判断还有下一页，怎样确认任务完成，超时后服务端任务是否继续，重试是否可能重复产生结果。按已知事实填写与当前对象有关的内容，未明确的行为列为待补项。

版本变化写出旧行为、新行为及影响。弃用说明保留已知的弃用版本、替代方式和迁移条件；移除时间仅在材料已明确时给出。

## 按证据组织故障排查

以读者能观察到的症状或错误码作入口。先写适用条件和现象，再列检查方法、检查结果及对应动作。原因未经确认时使用“可能”，并给出能够区分这些原因的检查。

优先安排容易执行、影响较小且能缩小范围的检查。每个分支交代何时继续、何时停止；重试要说明适用条件，清理或恢复操作要说明影响。材料只支持定位问题时，写到已知结论，并明确尚缺的处理办法。

需要进一步求助时，列出能支持诊断的信息，如版本、错误码、请求标识和已做的检查。日志摘录保留诊断所需的内容，对凭据和个人信息作脱敏处理。

## 解释机制与技术取舍

先给读者理解后文所需的最小概念，再说明系统中的关系。按主题追踪数据如何流动、状态如何变化，或一次请求经过哪些组件；让同一对象始终使用同一名称。

把机制、结果和限制连起来。比如说明缓存时，交代读取路径、更新方式与数据新鲜度之间的关系；介绍方案取舍时，在相同条件下比较读者关心的指标。区分材料中已确定的因果关系、观察到的现象和待验证的假设。

图示需要帮助理解具体关系，节点名与正文一致，箭头说明方向或含义，关键结论仍用文字交代。比喻之后说明对应关系及适用边界，保留工程上的精确定义。

## 按实际阅读路径检查

- 操作型内容：读者能确认适用环境，准备输入，完成每一步，并判断成功或进入明确的排查分支。
- 参考型内容：读者能按真实名称找到条目，区分取值、默认行为、限制和版本差异。
- 解释型内容：读者能理解主要关系、结论依据和适用边界，不依赖未介绍的项目知识。

改写后，将命令、标识符、单位、边界、状态和版本范围与材料逐项对照。允许且具备环境时，在隔离环境中试走操作路径；否则说明核对范围与未验证项。验证记录按任务需要交付，不把编辑过程混入面向读者的正文。
